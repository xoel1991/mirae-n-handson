# 레거시 모듈 문서화

- 분석 대상 폴더(`$ARGUMENTS` 의 모듈 경로)와 `db/` 의 파일은 읽기만 한다. 수정 · 삭제 · 쓰기 요청(POST 등)은 하지 않는다.
- 근거 라인을 댈 수 없는 내용은 적지 않고 "미확인"으로 남긴다.

## 0. 모듈명 정하기

| 모듈 경로 | `<모듈명>` |
|---|---|
| `legacy/item-bank-php` | `item-bank` |
| `legacy/assignment-thymeleaf` | `assignment` |
| `legacy/grade-mssql` | `grade` |

- 산출물 폴더는 폴더 이름이 아니라 위 `<모듈명>` 을 쓴다: `docs/<모듈명>/`
- 표에 없는 경로면 멈추고 모듈명을 묻는다.

## 1. 계획 먼저 제시

- 파일 목록(Glob)과 크기만 보고 단계 · 읽을 파일 · 산출물을 짧게 제시한 뒤 시작한다.
- 범위 제한이 있으면 계획에 "범위 밖"으로 적은 항목은 다루지 않는다.

## 2. 진입점 → `ARCHITECTURE.md`

- 모듈 개요, 폴더 구조, 진입점 표(URL · 파일 · 처리 함수 · 줄번호).
- 저장한 뒤 다음 단계로 넘어간다.

## 3. 의존 관계 → `ARCHITECTURE.md` 에 추가

- 구조 그림과 호출 표(호출하는 쪽 → 호출되는 쪽, 근거 줄번호), 가장 긴 함수 3개, 미확인 목록.
- 호출 방향은 호출문이 있는 줄을 열어 확인한 뒤 적는다. 저장한 뒤 넘어간다.

## 4. 데이터 흐름 → `ERD.md`

- 테이블 목록, 테이블 관계(mermaid), 테이블별 읽기 · 쓰기 위치, 화면별 흐름 요약, 미확인.
- 관계마다 **선언**(FK 제약, 근거 `스키마파일:줄번호`)과 **추정**(FK 없이 JOIN · WHERE · 컬럼 이름으로만 보이는 관계, 근거 SQL `파일:줄번호`)을 구분해, 관계 표와 mermaid 선 라벨에 `(선언)` · `(추정)` 을 붙인다.
- 뷰 · 트리거 · 프로시저는 모듈 폴더 밖(`db/**/init/*.sql`)까지 찾아 정의를 확인한다. 저장한 뒤 넘어간다.

## 5. 비즈니스 규칙 후보 → `BUSINESS-RULES.md`

규칙마다 아래 형식을 그대로 쓴다. 번호는 `BR-01` 부터 매긴다.

```markdown
### BR-NN <규칙 한 줄 요약>
- **규칙**: 입력 · 조건 → 결과를 코드 값 그대로 적은 문장
- **근거**: `파일:줄번호` (저장소 루트 기준)
- **근거 코드**:
  ```<언어>
  <실제 코드 그대로 인용>   // 파일:줄번호
  ```
- **확신도**: 확실 | 추정 | 확인 필요
- **비고**: 주석과 코드가 다른 곳, 같은 규칙의 다른 구현, 실행 확인 결과 등
```

- 끝에 매직 넘버 · 매직 값 표와 "주석과 코드가 다른 곳" 모음을 둔다.

## 6. 하지 말 것 (item-bank 검증 이력에서 실제로 틀린 유형)

- **화면 표시용 값을 SQL 근거로 인용하지 않는다.** BR-15 는 정렬 방향 근거로 `search.php:330`(화면 링크용 기본 방향)을 댔지만, 실제 방향은 SQL 분기 `:276-316` 이 정했다. 같은 함수 안의 값이라도 그 줄이 쿼리 · 저장 · 표시 중 무엇에 쓰이는지 확인한다.
- **주석을 규칙의 근거로 쓰지 않는다.** CX-03 은 `:107` 주석 "정확히 일치"를 믿고 적었지만, 코드와 스키마 collation 상 대소문자를 구분하지 않았다. 주석과 코드가 다르면 코드를 따르고 비고에 불일치를 적는다.
- **모듈 폴더만 보고 "미확인"으로 끝내지 않는다.** CX-12 는 뷰 `v_item_public` 정의가 `db/mariadb/init/01-schema.sql` 에 있어 필터 조건을 놓쳤다.
- 존재하지 않는 함수 · 테이블 이름, 코드에 없는 인용 코드, 코드에 없는 규칙(일반 상식 · 추측)을 쓰지 않는다.

## 7. 자체 점검

- 문서의 함수 · 테이블 · 뷰 이름은 `grep` 으로, 인용 코드는 `grep -F` 로 실제 파일과 대조한다. 0건이 아니면 고친다.

## 8. 사람이 표본 점검할 규칙 3개 추천

- 아래 기준으로 3개를 골라 ID · 이유 · 열어 볼 `파일:줄번호` 를 표로 보고한다.
  1. **가장 그럴듯한 규칙** (너무 자연스러워 검증 없이 넘어가기 쉬운 것) — 반드시 포함
  2. 주석과 코드가 다른 규칙
  3. 근거 라인이 여러 곳에 흩어진 규칙
- 사람이 점검한 결과는 `BUSINESS-RULES.md` 끝 "검증 이력" 표(날짜 · 대상 · 방법 · 판정 · 조치)에 적는다.
